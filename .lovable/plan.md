# Clinic Management System — KILINIKA G/GALEESSA TUUDII (Two D Medium Clinic)

Version 1 has three departments: Reception, OPD and Laboratory. They all share one patient database. All development data is fictional.

Note: I could not find the clinic logo or the lab request form in this chat. Please attach both before Phase 1 starts. Until then I will use a text logo and a standard lab request layout.

## 1. System architecture

```text
Browser (React + TypeScript + Tailwind, royal blue / white / light blue)
   |
TanStack Start app (pages + server functions; permissions checked on every call)
   |
Lovable Cloud (PostgreSQL + Auth + row-level security + audit triggers)
```

- One shared patient record. Each department reads and writes only its own part of it.
- Roles live in a separate `user_roles` table. Access is enforced in the database (RLS), not only in the screens.
- Every status change (queue, lab request) records a timestamp and the staff member who made it, for traceability.
- Lab reports and patient cards print from the browser using print-friendly layouts (A4 / A5).

## 2. Staff roles and permissions

| Area | Admin | Receptionist | OPD Clinician | Lab Technician |
|---|---|---|---|---|
| Staff accounts and roles | Full | – | – | – |
| Test catalogue and settings | Full | – | – | View |
| Register / edit patient demographics | Full | Full | View | View (basic) |
| Appointments and queue | Full | Full | View, call next, complete | – |
| Vitals | View | Optional entry | Full | – |
| History, diagnosis, treatment notes | View | – | Full | – |
| Create lab requests | View | – | Full | – |
| Specimen collection, processing, result entry | View | – | – | Full |

Staff accounts are created only by the administrator. There is no public sign-up.

## 3. Patient workflow

```text
RECEPTION                    OPD                              LABORATORY
Search patient
 ├─ found ─┐
 └─ new: register (MRN) ─┤
Check-in / appointment ──> Queue: waiting
                             Clinician calls patient
                             Vitals, history, complaint
                             Lab request ───────────────> Worklist: requested
                                                            Specimen collected
                                                            Processing
                                                            Result entered
                                                            Verified ── report printable
                             Result shows on the visit <──┘
                             Diagnosis, treatment notes
                             Visit completed ──> Queue: done
```

Status values:
- Visit / queue: `waiting → in_consultation → awaiting_lab → in_consultation → completed` (also `cancelled`, `no_show`).
- Lab request item: `requested → collected → processing → resulted → verified` (also `rejected`, with a reason, for example a haemolysed sample).

Patient ID format: `TDC-YYYY-000001`, generated by a database sequence so it is unique and cannot be edited.

## 4. Screens and navigation

The layout is the same for everyone. A royal-blue left sidebar shows the logo and only the menus allowed for the user's role. A top bar has patient search, the user's name and role, and logout. The main area uses white cards on a light-blue background.

- **Login**: clinic logo, email and password.
- **Dashboard** (per role): today's counts for registered patients, waiting, in consultation and pending labs.

Reception
- Patient Search: search by name, MRN or phone, with a results table.
- Register Patient: a form for name, sex, date of birth or age, phone, address (kebele/woreda), emergency contact, and allergies alert. Prints a patient card.
- Patient Profile: demographics, visit history, and lab results (read-only for reception).
- Appointments: a day or week list plus a booking form.
- Walk-in / Check-in: pick a patient, add a visit, and assign a queue number.
- Queue Board: a live list of today's queue and statuses.

OPD
- My Queue: waiting patients, with a "Call next" button.
- Consultation workspace (one page, with tabs): Vitals, Complaint and History, Examination, Lab Requests (test checklist modeled on the clinic form), Results (live, showing abnormal values), Diagnosis, Treatment Notes, and Complete visit.
- Patient Record: full timeline of visits, vitals trend and lab history.

Laboratory
- Worklist: filters by status and date. Urgent requests are shown first.
- Request detail: collect specimen (sample ID and time), start processing, enter results (with reference ranges and abnormal flags), and verify.
- Printable Lab Report: clinic header and logo, patient details, results table, and the names of the technician who entered and the one who verified.

Admin
- Staff and roles, the test catalogue (tests, panels, units, reference ranges, specimen type), clinic settings and the audit log.

## 5. Database tables

```text
profiles(id → auth.users, full_name, phone, active)
user_roles(user_id → auth.users, role: admin|receptionist|clinician|lab_tech)
patients(id, mrn UNIQUE, first/middle/last name, sex, dob, phone, address,
         emergency_contact, allergies, created_by, created_at)
appointments(id, patient_id → patients, clinician_id → profiles,
             scheduled_at, reason, status)
visits(id, patient_id, appointment_id NULL, visit_type walk_in|appointment,
       queue_number, queue_date, status, assigned_clinician_id,
       checked_in_by, checked_in_at, completed_at)
vital_signs(id, visit_id, bp_sys, bp_dia, pulse, temp, resp_rate, spo2,
            weight, height, recorded_by, recorded_at)
consultations(id, visit_id UNIQUE, chief_complaint, history_present_illness,
              past_history, examination, treatment_notes, clinician_id)
diagnoses(id, consultation_id, description, icd10_code NULL, type primary|secondary)
lab_tests(id, code, name, category, specimen_type, unit,
          ref_low, ref_high, ref_text, active)
lab_requests(id, visit_id, patient_id, requested_by, priority routine|urgent,
             clinical_notes, status, created_at)
lab_request_items(id, lab_request_id, lab_test_id, status,
                  specimen_id, collected_by/at, processed_by/at,
                  result_value, result_text, abnormal_flag,
                  resulted_by/at, verified_by/at, rejection_reason)
audit_log(id, user_id, table_name, record_id, action, changed_at, diff)
```

Relationships: a patient has many visits and appointments. A visit has vitals, one consultation, and lab requests. A lab request has many items, and each item points to one catalogue test. Results go back to OPD because every item is linked to `visit_id` and `patient_id`, and clinicians can only see items whose status is `verified`.

## 6. Phased implementation

1. **Foundation**: enable Lovable Cloud, set up the theme and logo, login, roles, admin staff management, the app layout with role-based menus, and the audit log.
2. **Reception**: patients (MRN sequence), search, registration, profile, appointments, check-in, queue board, and fictional sample patients.
3. **OPD**: My Queue, the consultation workspace (vitals, history, diagnosis, notes), patient record timeline.
4. **Laboratory**: test catalogue seed, lab requests from OPD, worklist, specimen, processing, results, verification, printable report, and verified results appearing in OPD in real time.
5. **Hardening**: dashboards, permission tests for each role, print polish, a security scan, and a backup/export review before real use.

## Technical notes

- TanStack Start server functions use auth middleware. RLS policies use `has_role()` (security definer).
- MRN comes from a Postgres sequence plus a trigger. Status changes go through server functions that check that each transition is allowed.
- Realtime subscriptions keep the queue board and lab worklist live.
- Seed data is fictional only and comes from migrations.
- Before real patient data goes in, the clinic should confirm it meets local health-data rules (Ethiopia), back-up procedures and staff password policies.
